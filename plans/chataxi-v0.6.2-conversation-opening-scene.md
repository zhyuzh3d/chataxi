# chataxi 0.6.2 对话场景开场白计划

## 1. 目标与不变量

“场景设定”只负责在对话开始时自动产生一条开场消息，不是角色设定、用户设定或永久提示词。非空场景在对话第一次进入且尚无普通历史时落成一条 `system` 消息；它不调用模型，也不触发角色回答。用户随后发送第一条消息时，现有回复流程照常重新组装全部角色信息和当前用户信息，并把这条场景消息作为历史的第一条提交给模型。

场景消息一旦落库，开场机制即完成。之后它与用户、角色消息使用同一套排序、显示、搜索、导出、编辑、请求组装和压缩规则：未越过概要边界时可以修改保存；被概要覆盖后按普通旧消息规则不再直接修改。不得把场景文本复制到角色提示词、用户资料、概要外的常驻字段或每轮专用注入分支。

角色设定和用户设定仍是每轮重新组装、永不参与历史压缩的持久指令。场景消息会正常进入压缩前缀；被覆盖后原消息不再进入模型上下文，只由概要表达仍然有效的故事状态。压缩概要在回复请求中也以 `system` 历史发送，与场景消息共用同一角色映射器，不再混入角色提示词。

## 2. 数据与一次性生命周期

对话在开场消息产生前只保存一个临时字段：

```js
conversation.openingSceneDraft = "故事开场文本"
```

对话页首次读取历史时执行一次幂等准备：若历史为空且草稿非空，写入普通消息并在成功后删除草稿字段。消息使用稳定 ID，避免写入成功但清理草稿失败时重复创建：

```js
{
  id: "opening-scene:" + conversationId,
  conversationId: conversationId,
  kind: "system",
  systemType: "scene",
  text: "故事开场文本",
  media: [],
  status: "done",
  createdAt: conversation.createdAt
}
```

进入页面时必须先完成该原子准备，再建立 `messageSnapshot` 和开放输入框，因此用户消息不可能抢在开场白之前。保存设置时若当前正处于尚无历史的对话页，直接调用同一个准备函数并刷新消息区；从对话列表保存时保留草稿，到下一次进入时产生消息。空草稿不产生消息。

已经存在用户或角色历史、但从未发送过场景消息的旧对话，不允许追溯插入“第一条消息”，避免伪造时间线或破坏已有概要边界；弹窗只说明该对话已经开始，不能再添加开场白。已经存在场景消息时，菜单直接编辑这条普通消息，不再读写 `openingSceneDraft`。实现不保留 `sent` 开关、场景副本或单独版本号。

## 3. 标准上下文合同

内部请求历史明确支持三种语义角色：`system`、`user`、`assistant`。`kind: "system"` 不得再经过“非 assistant 一律映射为 user”的旧分支。上下文流程统一为：

1. `context.prepare` 仍按现有概要边界返回全部未压缩完成消息；场景消息只是其中的第一条。
2. 若存在概要，构造一条仅用于本次请求的普通规范消息：`{ kind: "system", systemType: "summary", text: summary.text }`，放在未压缩历史之前。
3. `applyToRole` 每轮只组装当前角色、其他角色参考和当前用户信息；删除其中的 `<conversation_summary>` 拼接。
4. `hydrateMessages` 按消息自身的 `kind` 产生规范角色，不识别“场景设定”业务规则。
5. 自动选角与正式角色回复调用同一个“概要 system 消息 + 未压缩历史”构造函数，保证两条路径的上下文一致。
6. 压缩输入把 `system` 消息转录为“系统：…”，场景自然位于待压缩历史中；压缩成功后边界前移，原场景不再出现。概要生成本身仍遵循现有增量算法，不增加场景保留特权。

持久角色/用户指令与历史 system 消息在内部合同中保持分离：前者是每轮 `instructions`，后者是有顺序、可压缩的 `input`。只有传输适配器可以因协议限制把二者合并到同一个原生 system 槽位，业务上下文层不得提前合并。

## 4. 六种协议的 system 角色映射

模型配置表中的官方、聚合、本地和自定义入口最终只落到 `catalog.apiStyles` 的六种 LLM codec。映射依据 `transportCodecId/apiStyle`，不得根据模型名称改变线协议：

| Codec | 持久角色/用户指令 | 场景或概要 system 历史 |
| --- | --- | --- |
| `openai-responses` | 顶层 `instructions` | 原生 system input；若目标能力不确认则走兜底 |
| `openai-chat` | 首个 system/developer 槽位，按配置表声明 | `role: "system"`；适配器可与首个 system 块按顺序合并 |
| `anthropic-messages` | 顶层 `system` | 按顺序并入顶层 `system` 内容块；不得放入只接受 user/assistant 的 `messages` |
| `gemini-interactions` | `system_instruction` | 按顺序并入同一 system instruction 内容 |
| `gemini-generate-content` | `systemInstruction` | 按顺序并入同一 system instruction parts |
| `ollama-chat` | 首个 `role: "system"` | 原生 system 消息；必要时合并为一个首部 system 块 |

合并只是协议编码，不改变本地消息身份、顺序、可编辑性或压缩边界。适配器对规范 system 消息使用 `systemType` 生成稳定标签：场景为 `[场景设定]`，概要为 `[历史概要]`；标签只用于让模型区分内容来源，不写回消息正文。

## 5. 未确认模型的兜底

LLM 解析能力增加 `systemRoleMode: "native" | "tagged-user"`。内置配置表中已明确覆盖的模型/入口使用 `native`；自定义、聚合或本地服务中未被配置表确认的模型使用 `tagged-user`，不能靠模型名称猜测 system 支持，也不在请求失败后自动重试。

`tagged-user` 模式把本轮所有首部 system 内容合并成一个规范 user 输入，顺序固定为：

```text
[角色与用户设定]
每轮重新组装的角色与用户信息

[场景设定]
尚未压缩的开场白
```

场景被压缩后，同一位置改为：

```text
[角色与用户设定]
每轮重新组装的角色与用户信息

[历史概要]
压缩概要
```

本地历史仍保存为 system，只有请求编码结果降级为 user。这样未知模型不会收到不支持的角色值，同时不会把场景误认为用户在当前轮提出的新要求。未知 `apiStyle` 仍必须阻止请求，因为没有请求体和响应解析合同；兜底只解决“已知 codec 下模型的 system 能力未知”，不能伪造新的传输协议。

## 6. 界面与普通消息行为

对话列表管理菜单和聊天页管理菜单都在“个人设定”下面增加“场景设定”。Sheet 使用一个最多 16000 字的文本框，并明确说明：开场白不会立即触发角色回复；进入空对话后会作为系统第一条消息发送。

消息产生后，Sheet 读取并保存原消息；聊天气泡中的编辑按钮也调用同一个普通消息编辑函数。system 消息显示为无头像的居中系统消息，名称为“系统”，保留时间、复制和编辑；不显示朗读、重新生成或角色头像入口。文字导出标为“系统”，搜索和会话预览按普通消息处理。

编辑继续服从现有概要边界：场景未压缩时直接 `putMessage`，不删除后续消息、不触发角色生成；已经压缩时与其他旧消息一样拒绝直接修改，并引导用户编辑现有“压缩上下文”。不得为了修改场景而删除概要、重跑压缩或建立场景专用覆盖层。

## 7. 实施顺序

1. 在 `store` 增加幂等的开场草稿落库函数和 system 消息查询；保持 `messages()` 只过滤 routing 诊断记录。
2. 在 `chat.render` 读取历史前完成开场准备；在两个对话菜单复用同一个场景 Sheet。
3. 扩展消息显示、导出、编辑标题和操作按钮，使 system 成为明确的第三种普通角色。
4. 在 `context` 中生成概要 system 规范消息，并从每轮角色提示中移除概要正文。
5. 在 `llm`/`middleware` 中让选角和正式回复共用规范历史，保持角色与用户资料每轮组装。
6. 在 `model-registry` 的解析能力中加入 `systemRoleMode`，在 `providers` 为六种 codec 实现 native 与 tagged-user 两条确定路径。
7. 同步 README、产品设计、版本号和直接合同测试；不改动 TTS、ASR、媒体、角色生成或压缩阈值。

## 8. 验收

- 空场景不产生消息；非空场景只产生一次，并始终早于第一条用户消息；重载、崩溃恢复和重复进入不重复创建。
- 开场落库不调用任何模型；用户首次发送后才触发选角/回复，请求同时含全部角色信息、当前用户信息和场景历史。
- 场景消息可以按普通消息编辑；编辑不触发回复、不删除后续消息，进入概要边界后按普通规则禁止编辑。
- 第一次压缩输入包含“系统：场景文本”；压缩后正式回复只携带一条 system 概要，不再携带原场景。
- 角色设定与用户设定始终逐轮重新组装，既不进入压缩输入，也不被概要替代。
- 六种 codec 分别断言 system 映射位置；未知模型断言使用 user 兜底并含精确的 `[场景设定]` 或 `[历史概要]` 标签；未知 codec 明确报错。
- 自动选角和正式回复看到完全相同的场景/概要历史，群聊唯一发言者保护保持不变。
- 搜索、导出、预览、删除对话和数据清理覆盖 system 消息；routing 诊断仍不进入普通历史。

直接检查范围为 `tests/runtime.test.mjs`、`tests/providers.test.mjs`、`tests/ui-flow.mjs` 与 `node tools/verify.mjs`。实现完成后通过当前局域网 DEV 通道增量同步并等待渲染确认；除非另有要求，不生成发布 ZIP、不安装稳定包、不做视觉验收或提交推送。
